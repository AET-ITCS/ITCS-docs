# 工程标准：工作清单制定规范 (Plan Standard)

本标准定义了项目中 `plan_工作标的简称.md` 文件的结构、格式和内容要求，旨在确保工程变更的透明度、可评审性和执行的可追溯性。

## 工作清单定义 (Plan and todo)

实施计划用于在开始任何重大变更之前，向团队/用户展示技术方案，获取反馈并获得批准。

### 1.1 文件命名与位置

- **文件名**: `plan_工作标的简称.md`
- **位置**: 本工程的 `docs` 目录下，如果docs中找不到最接近本次工作标的简称的子目录，可以新建子目录。

### 1.2 核心结构

计划文件包含以下部分：

#### A. （·必选·）目标描述 (Goal Description)

简要描述问题背景、拟解决的问题以及变更完成后达到的效果。

#### B. （·可选·）用户评审项 (User Review Required)

使用 GitHub Alert ([!IMPORTANT], [!WARNING]) 突出显示需要用户特别关注、决策或批准的内容。

#### C. （·必选·）拟议变更 (Proposed Changes)

按组件或功能模块组织变更点。

- 使用 `[NEW]`, `[MODIFY]`, `[DELETE]` 标识文件操作。
- 必须使用绝对路径或可点击的链接引用文件。

#### D. （·可选·）开放问题 (Open Questions)

列出所有尚未确定的设计细节或需要用户澄清的问题。

#### E. （·必选·）验证计划 (Verification Plan)

- **自动化测试**: 列出需要运行的测试命令或脚本。
- **人工验证**: 描述手动检查步骤或 UI 验证流程。

---

#### F. （·必选·）任务清单 (TODO List)

任务清单是执行阶段的 TODO 列表，用于跟踪工作进度。

##### 文件命名与位置

- **文件名**: 与`plan_工作标的简称.md`是同一个文件
- **位置**: `plan_工作标的简称.md`的末尾处

##### 格式要求

- 必须使用 Markdown 复选框：
  - `[ ]`: 未开始
  - `[/]`: 进行中
  - `[x]`: 已完成
- 任务应具有原子性，复杂的步骤应使用缩进的子任务。

---

### 1.3 最佳实践 (Best Practices)

- **保持简洁**: 避免长篇大论，使用列表和短句。
- **可链接性**: 所有涉及的文件和目录应尽可能提供链接。
- **动态更新**: 随着工作的深入，及时更新 `plan_工作标的简称.md` 中细节进展的状态和 `plan_工作标的简称.md` 中的设计决策。
- **引用规范**: 参照 `docs/工程标准/standard_工作清单.md` 进行编写。
